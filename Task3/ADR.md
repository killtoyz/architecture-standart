### <a name="_qmphm5d6rvi3"></a>**Решение**
Диаграмма контекста

Диаграмма контейнеров (монолит)
Диаграмма контейнеров (микросервисы)

Самым важным мне показались следующие позиции:
1. Не перегружать АБС, не использовать API напрямую
2. Возможность оставить весь БП по депозитам в АБС
3. По максимуму переиспользовать текущий стек технологий
4. Сделать задел на будущий переход к микросервисной архитектуре приложения ИБ
5. Возможность быстрого горизонтального и вертикального масштабирования, т.к. неизвестно кол-во потенциальных новых пользователей ИБ

Исходя из этого были приняты следующие решения:
1. Использовать брокер сообщений между системами: Сайт - Колл-центр, ИБ - АБС, АБС - ИБ. Это позволит АБС самому регулировать нагрузку на свои системы и т.к. процесс все ещё остается в АБС, то такое решение не создает проблем с откликом в самих приложениях (ИБ и Сайте)
2. Несовместимость ИБ с Kafka. Решается: через интеграционный адаптер (монолитный вариант) или через новый сервис «Управление депозитами» (микросервисный вариант)
3. Использовать витрину данных для публикации актуальных ставок и информации о депозитах. Это также позволит Сайту и ИБ не зависеть от АБС и не использовать API, а также позволяет загружать данные быстро для клиента
4. Т.к. важно переиспользовать текущий стек, то были по максимуму выбраны уже те технологии с которыми знакома команда
5. Чтобы сделать задел на будущий переход к микросервисной архитектуре мы специально не завязывались на API АБС, отказались от использования стороннего СМС-сервиса (и опять же использования АБС для этих целей), предположили о возможных микросервисах ИБ
### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **Перевести весь БП в ИБ**

**Недостатки, ограничения, риски**

Недостатки:
* Процесс согласования ставок и ведения депозитных условий уже есть в АБС, его пришлось бы повторить в ИБ
* Сотрудникам бэк-офиса депозитов понадобился бы интерфейс в ИБ, хотя сейчас они работают в АБС и XLS
* Данные о депозитах разойдутся между ИБ и АБС, понадобится их постоянная синхронизация

Ограничения:
* Нужна миграция данных из АБС в ИБ, а это объём работ, несоразмерный MVP
* ИБ инфраструктурно работает на одном ЦОД, а АБС на двух, что плохо для отказоустойчивости

Риски
* Срыв сроков реализации из-за объема работ

2. Использовать API АБС

Недостатки: 
* В будущем все равно пришлось бы отказаться от использования API. Лишняя работа
* Неочевидное кол-во новых пользователей ИБ могло бы создать слишком большую нагрузку на АБС
	* Если АБС недоступна или перегружена, ИБ не может принять заявку, а требование 99,9% нам этого не позволяет
* Отклик интерфейса ИБ определялся бы скоростью ответа АБС, а миллисекундного отклика при перегруженной БД АБС не достичь

Ограничения:
* БД АБС уже перегружена, а масштабироваться АБС может только вертикально

Риск:
* Если АБС откажет, то откажет и ИБ

3. Монолит с адаптером ИЛИ микросервисы
Оба решения имеют место быть, микросервисы будет сложнее разработать и дольше, но лучше для будущей поддержки. Монолит для MVP подходит лучше, но хуже для будущего развития
